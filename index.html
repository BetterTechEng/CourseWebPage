Two Ways of Working, in Plain Terms

SDLC (Software Development Lifecycle) is the familiar way: people plan, build, and test in stages, one after another. ADLC (Agentic Development Lifecycle) is the new way: AI agents build and test continuously, while people direct and review. This Program is about moving your QA team from the first row below to the second.

Old way — SDLC
Plan → Build → QA tests, at the end → Release

QA is one slow stage near the end. If it runs late, the release runs late.

New way — ADLC
Agents build ⇄ Agents test, every change ⇄ Agents fix

People direct and review. Testing happens constantly, not once at the end — so QA stops being the bottleneck.

Your team's new job: tell the agents what "correct" looks like for your storefront, check their judgment on the cases that matter, and step in when something needs a human call.

How You Know an Agent Is Ready to Ship

Testing an agent isn't like testing a script. Before a checkout assistant, a returns bot, or a pricing agent goes live, your team needs a fast way to tell if it's ready — not a perfect test suite on day one, just enough to catch obvious failures, compare one version against another, and avoid shipping a change blind.

Start small, not perfect

A first set of real tasks, not a full suite

Most teams start with a small set of representative tasks: a few pulled from expected use cases, others from manual testing, support tickets, or known edge cases. It's a regression suite for a system that talks and decides, not one that only executes steps. Real traffic makes it stronger later — it doesn't need to start there.

Datasets & metrics

So a fixed failure doesn't quietly come back

Datasets capture what your team has already learned, so a bug fixed once doesn't resurface after a prompt change or model upgrade. Some checks have one right answer — did the agent apply the correct discount, pull the correct order ID. Others don't — did the agent explain a delay clearly, or know when to hand off to a person. Those get judged against criteria, not a single correct answer.

Experiments

Proof a change actually helped

Experiments run a new prompt, model, or tool setup against the same evaluation set as the last version, so your team can see whether a change made things better or worse before it ever reaches a customer.

Simulation

Testing a conversation, not just an answer

Many agents don't just answer once — they hold a conversation, look things up, and adjust. A support agent may need to calm a frustrated shopper, check an order, and decide whether to escalate. That needs a simulated back-and-forth, not a single question and answer.

Put together, this is what "testing" means in the ADLC: turn what "good" looks like into a dataset, the dataset into an experiment, and the experiment into a better version of the agent. Once it's live, real conversations feed back into the same datasets, so the eval set keeps getting harder and more realistic. Further reading: multi-turn simulation for agent evals.

Built on the Models Your Team Already Trusts

No single model does every job well. Your team learns which one to reach for, in the tools they already use.

GitHub Copilot

In-IDE automation authoring for checkout, cart, and API test suites — turns a spec comment into a first-draft test file and drafts self-healing selectors when a PDP or cart UI ships a change.

Claude

Long-context reasoning over pricing rules, tax logic, and incident history — requirements-gap detection on promo/discount specs and root-cause hypotheses with a code-level fix.

Gemini

Multimodal triage across checkout screenshots, payment-gateway logs, and session recordings — useful when a defect is visual or spans storefront, payment, and fulfillment services.

How We Get Your Team There

Four sprints. Each one hands your team a new way of working, not just a new tool.

Phase 1 — Learn to direct agents, not write scripts

Your team shifts from writing every test by hand to setting up AI agents for UI, API, and database testing, then reviewing their work.

Phase 2 — Let agents draft the tests

Agents read specs and write first-draft test coverage. What used to take days now takes hours.

Phase 3 — Let agents keep tests working

When the UI changes, agents fix the tests instead of engineers. Your team reviews and approves the fix.

Phase 4 — Let agents triage defects first

Agents look at past incidents to point straight to the likely cause of a new bug, and how risky each release is, before you ship.
